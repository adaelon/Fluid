# 追问回答一致性与历史恢复契约切片方案

> 状态:实施中（2026-08-11 `S-QCONS-1/2` 已完成;历史 REST 规范化与整体验收仍待后续切片）。领域术语沿用 `CONTEXT.md`,关键权衡见 `docs/adr/0029-追问方向声明门禁与历史REST规范化.md`。
> 本方案修复两个独立故障:回答误选 QueryMap 空方向分支,以及历史 REST 省略空 `sources` 导致恢复在 Markdown 渲染前崩溃。

## 目标与边界

**做**:

- 由后端根据最终 `QueryMap.direction` 派生唯一、可机器校验的回答首行,不再让模型自行选择“有方向/空方向”分支。
- current 与 selected-file-set 两条追问路径共用同一首行门禁、一次同边界纠正和持久化终验。
- 首次首行违约在任何回答 delta 可见前纠正一次;纠正仍失败时只发 `error`,不发 `done`,不追加持久轮次。
- 后端读入兼容旧历史中被省略的 `sources`,但持久记录重新序列化及历史 REST 输出都显式返回 `sources: []`。
- 前端只在 `api.ts` 的历史响应边界兼容归一化旧省略形态,内部 `PersistedQueryEvidence.sources` 继续保持必填数组。
- 用后端真实响应形态覆盖历史选择,并证明恢复完成后原回答能够进入现有 Markdown 渲染链。

**不做**:

- 不声称确定性判断整篇自然语言的全部语义真伪;本门禁只冻结“方向存在性 + 方向条数 + 至少一个方向证据引用”这组可判定不变量。
- 不用第二个 LLM、LLM-as-judge、embedding 或模糊语义分类器裁判回答是否正确。
- 不改变 `QueryMap`、`EvidenceCatalog`、取源、图谱、Web Search、追问轨迹或源码版本算法。
- 不新增回答撤回/替换帧,不把完整首答缓存到结束后才一次性显示,不改变合法回答首行通过后的逐 delta 呈现。
- 不修改 Markdown 文本、`markdown-it`、DOMPurify、KaTeX 或 `QueryPanel.vue` 的渲染实现。
- 不把 `sources ?? []` 散落到 `queryWorkspace.ts`/组件消费点,也不把前端类型简单改成到处可选。
- 不提升 `QUERY_THREAD_SCHEMA_VERSION`;旧 JSON 的省略形态继续由 `#[serde(default)]` 兼容读取。
- 不改变实时 `QueryFrame::Evidence` 的可选空数组形态;现有 reducer 已在 WebSocket 边界执行 `frame.sources ?? []`。

## 已确认根因

- 同一个后端 `QueryMap` 已被注入最终 Prompt、发给前端并随完成轮次保存;事故数据含 5 个参与者、17 条 `direction` 与代码证据 `E1`,不存在缓存或前后端 map 错配。
- current Prompt 与 selected-file-set Prompt 只声明“`direction` 为空时明确说明为空”,没有给非空分支一个反向、可校验的输出契约。
- `stream_query_answer` 当前边收供应商 delta 边原样发给前端;`persist_query_completion` 只拒绝空答案并收集已知 E# 引用,不会拒绝“非空 map + 空方向声明”。
- `QueryEvidenceState.sources` 同时带 `#[serde(default, skip_serializing_if = "Vec::is_empty")]`;因此旧记录可读,但 GET 历史在空数组时真实返回 `{"status":"unverified"}`。
- 前端 `PersistedQueryEvidence.sources` 声明为必填,历史恢复却直接调用 `turn.evidence.sources.map(...)`;异常发生在轮次恢复阶段,`renderTraceAnswers` 尚未运行。
- 现有历史测试夹具固定写出 `sources: []`,没有覆盖服务端真实的字段省略形态;同一原始回答单独进入现有 renderer 能正常生成标题、强调、分隔线与表格。

## 冻结契约

### 1. 后端拥有方向声明

实现以 `QueryMap.direction.len()` 派生内部契约,模型不得自行计算方向条数:

```rust
enum QueryDirectionState {
    Empty,
    Present { step_count: usize },
}

struct QueryAnswerContract {
    direction: QueryDirectionState,
    expected_preamble: String,
    direction_evidence_ids: BTreeSet<String>,
}

fn query_answer_contract(map: &QueryMap) -> QueryAnswerContract;
fn validate_query_answer(answer: &str, map: &QueryMap) -> Result<(), QueryAnswerViolation>;
```

首个非空行只有两种规范形态:

| `QueryMap.direction` | 必须逐字匹配的首个非空行 |
| --- | --- |
| `[]` | `方向图状态：没有可核验的跨组件方向。` |
| 长度为 `N > 0` | `方向图状态：已核验 N 条跨组件方向。` |

- `N` 由后端以十进制写入最终 Prompt;Prompt 不再保留让模型判断 `direction` 是否为空的条件句。
- 两个最终 answer Prompt 都提供完整的 `expected_preamble`,并要求它成为首个非空行;规划 Prompt 不承担此契约。
- 首行按 `\r\n`/`\n` 等价、去除行首尾空白后比较;正文不得再次出现以 `方向图状态：` 开头的声明。
- 非空方向的完整回答必须至少引用一个来自 `map.direction[*].evidenceIds` 并存在于 `map.evidence` 的 `[E#]`;只引用 walkthrough 或未知 E# 不满足方向证据门禁。
- 去掉首行后正文仍必须非空;仅复述规范首行不构成完整回答。
- 代码围栏和行内代码中的同形文本不参与声明或 E# 判定,继续复用现有 `query_answer_prose` 口径。
- 该 validator 保证规范方向声明、条数与方向证据的结构一致性;actor/function 的自然语言解释是否充分仍不冒充为可确定判定。

### 2. 首行纠正先于可见回答

```text
prepare final system/user + QueryMap + EvidenceOutcome
  -> status* -> map -> evidence
  -> answer attempt 1
       buffer first non-empty line (bounded)
       -> matches expected preamble:
            emit validated preamble + remaining delta stream
            -> terminal validate -> append turn -> done
       -> malformed / wrong branch / wrong count:
            abort attempt 1 before any answer delta
            -> correction attempt 1 (same snapshot and boundaries)
                 -> preamble valid: emit only corrected answer -> terminal validate
                 -> invalid/provider error: error, no done, no turn
```

- 首行缓冲必须有固定字符上限;超过上限仍未形成规范首行即视为协议失败,不能无界等待。
- 纠正请求逐字复用最终 `system` 与已经追加网页证据的最终 `user`;只附加期望首行、无效前缀和确定性错误。
- 无效输出明确标为“协议样本,不是事实”;纠正不得重跑 source planner、Web Search、QueryMap/EvidenceCatalog 组装或重新读取另一份配置快照。
- 只有首行 parse/validation 失败允许纠正一次;首次 provider/transport 失败、首行通过后的流错误、正文为空、重复声明或方向证据终验失败都直接 `error`。
- 首行通过后沿用现有 delta 流;本方案不撤回已发 delta。若完成终验才发现正文违约,partial 仍按现有错误态暂存,但绝不 Markdown 完成、绝不进入历史或后续 `QueryTrace`。
- current 与 selected-file-set 必须调用同一个门禁函数,不得复制两套关键词或纠正计数。
- `persist_query_completion` 在 `append_turn` 前重复执行完整 validator;调用方即使绕过流式门禁也不能写入不合格轮次。
- 只有 `append_turn` 成功后才允许发 `done`;任何门禁、纠正或存储错误均保持 `error` 为唯一终帧。

### 3. 历史证据数组采用规范输出、宽容输入

```typescript
type PersistedQueryEvidenceWire = {
  status: EvidenceStatus
  sources?: SourceLink[]       // 只描述旧/异版本输入
  warning?: string
}

type PersistedQueryEvidence = {
  status: EvidenceStatus
  sources: SourceLink[]        // api.ts 之后的唯一内部形态
  warning?: string
}

normalizeEvidence(wire) = {
  ...wire,
  sources: Array.isArray(wire.sources) ? wire.sources : [],
}
```

- Rust `QueryEvidenceState.sources` 保留 `#[serde(default)]` 以读取旧记录,移除空数组的 `skip_serializing_if`;新落盘记录与 REST 序列化均显式含数组。
- GET 历史读到旧 `{ "status": "unverified" }` 时不改写磁盘文件,但响应必须是 `{ "status": "unverified", "sources": [] }`。
- `createQueryThread`、`getQueryThread` 与 `forkQueryThreadCurrent` 的 JSON 都经过同一个 `normalizeQueryThread` 边界;零轮次响应自然不产生额外字段。
- `queryWorkspace.ts`、`QueryPanel.vue` 与呈现快照只消费规范内部类型,继续直接 `.map`;如果这里再出现 `?? []`,视为边界泄漏而不是修复。
- 缺失 `sources` 归一化为空数组;存在但不是数组属于坏响应,必须抛出 API 契约错误,不能静默吞成空数组。
- `warning` 继续可选,`evidence: null` 的语义不变;本刀不把没有 evidence 的轮次伪造成 `unverified`。

### 4. 失败与结果矩阵

| 场景 | 可见回答 | 终帧 | 持久轮次 |
| --- | --- | --- | --- |
| `direction.len() = 17`,首答声明为空,纠正声明 17 | 只有纠正回答 | `done` | 追加 1 轮 |
| `direction.len() = 17`,两次均声明为空 | 无回答 delta | `error` | 不追加 |
| `direction = []`,首答使用规范空方向首行且正文非空 | 首答 | `done` | 追加 1 轮 |
| 首行正确,正文无方向 E# | partial/error 态 | `error` | 不追加 |
| 首行正确,流中断或正文为空 | partial/error 态 | `error` | 不追加 |
| 历史 evidence 旧形态省略 `sources` | 正常恢复 | REST 200 | 内部为 `[]` |
| 历史 evidence 的 `sources` 为非数组 | 不恢复 | API 契约错误 | 不污染 workspace |

| current map 含 17 条方向,模型首答走空分支 | 错首行零 delta;同 map/evidence 纠正一次;仅纠正回答 `done` 并入历史 |
| selected map 非空,两次走空分支 | 单个 `error`;无错误回答 delta、无 `done`、无新增 turn |
| selected map 的 `direction=[]` | 规范空方向首行通过,正文正常流式并持久化 |
| 非空方向回答只引用 walkthrough E# | 终验失败,不持久化 |
| 首行正确后供应商中断 | 保留现有 partial/error 行为,不持久化、不进入后续轨迹 |
| 旧线程 JSON 省略 evidence.sources | store 可读;GET 返回 `sources: []`;读取不改磁盘 |
| 新线程 evidence.sources 为空 | 磁盘与 GET 均显式 `sources: []` |
| 前端收到旧省略形态 | API 边界归一化;历史选择成功;Markdown 标题/强调/分隔线/表格渲染 |
| 前端收到 `sources: {}` | 明确 API 契约错误;不把坏线程写入当前 workspace |
| 刷新浏览器/重启 Fluid | 规范历史仍可恢复;没有 `.map` 异常,原回答不变 |

## 验证纪律

- LLM 只产候选回答;方向状态、条数、方向 E#、帧序与持久化结果由 Rust validator、route mock 和文件系统裁判。
- 两个 bug 都必须先用事故形态得到稳定红测,再改实现转绿;不得通过把 fixture 补成理想字段或删除错误回答来“修复”测试。
- 一次纠正必须断言真实 LLM 请求序列与最终 system/user 边界,不能只数日志行。
- 失败原子性至少同时断言“错误首答零 delta / 无 `done` / turnCount 不变”;三项缺一不可。
- REST 契约必须同时检查序列化 JSON 与前端运行时值;TypeScript 声明、Rust struct 或人工阅读任一项都不能单独充当验收。
- Markdown 验收从历史 API 原始形态开始,经过 normalizer、workspace 恢复再进入现有 renderer;只对 renderer 单独喂字符串不算本 bug 回归。

## 领域对齐完成

`追问方向图`、`追问器`、`追问线程`、`项目追问历史` 与 `证据状态` 均沿用 `CONTEXT.md` 现有定义;新增的首行契约与 REST 规范形态属于实现边界,不引入新领域术语,零未解析符号。
