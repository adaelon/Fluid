# 文件定向两阶段生成切片方案

> 状态:实施中（2026-08-08）;`S-ORI2-1`、`S-ORI2-2`、`S-ORI2-3` 已完成,下一刀为 `S-ORI2-4`。领域术语沿用 `CONTEXT.md`,关键权衡见 `docs/adr/0025-文件定向骨架先行与函数角色分批生成.md`。
> 本方案只重构 `/api/orient` 缓存未命中的生成编排；最终 `FileOrientationCard`、WebSocket 帧、前端激活闸门和证据校验语义保持不变。

## 目标与边界

**做**:

- 阶段 A 只生成 `purpose/actors/types/coreFlows/walkthrough/invariants/evidence`,独立校验后冻结 actor、flow、evidence ID。
- 阶段 B 按后端确定的函数批次生成 `functionRoles` 与批次内 `supportingCapabilities`,每批只能引用阶段 A 的合法 ID 和本批次 `fnId`。
- 每个阶段 B 批次独立解析、校验；模型协议错误允许携带确定性错误定向纠正一次。
- 全部批次成功后由后端按 roster/批次顺序确定性合并,再执行现有 `FileOrientationCard::validate`。
- 只有整卡最终校验和调用后上下文复验都成功,才调用一次 `put_orientation` 并发送 `card -> done`。
- 第一版串行执行函数批次；缓存未命中的整次重试会重新运行阶段 A、全部阶段 B,大文件还会重新运行现有源码规划。

**不做**:

- 不引入 `response_format`、JSON Schema 供应商能力或新的 LLM 接口假设。
- 不放宽 actor/flow/evidence 引用、函数覆盖、源码路径、行号、bounded-source 或最终整卡校验。
- 不持久化阶段 A、单批结果、纠正记录或失败现场,也不增加断点、恢复、批次身份和半成品缓存。
- 不改变 `FileOrientationCard` 的线格式、`ORIENTATION_SCHEMA_VERSION`、`/api/orient` 帧种类或前端代码。
- 不并发发出函数批次,不在后端猜测、补写或语义合并模型缺失的引用。

## 已确认的现状缺口

- `context_assembler.rs:build_orientation_prompt/build_bounded_orientation_prompt` 当前要求一次输出整卡全部语义字段。
- `llm_proxy.rs:parse_orientation_card` 当前一次解析骨架、函数角色和外围能力。
- `routes.rs:run_orientation_emitting` 在源码准备后只调用一次定向生成；大文件是“一次源码规划 + 一次整卡生成”。
- `orientation.rs:FileOrientationCard::validate` 已有最终整卡校验,但没有可在阶段 A 或单个阶段 B 批次完成后调用的中间校验边界。
- `cache_store.rs:put_orientation` 已具备“最终校验通过后才创建缓存目录”的基础,两阶段实现必须继续只从最终合并点调用它。

## 已冻结中间契约

### 1. 阶段 A 定向骨架

```rust
struct OrientationSkeleton {
    purpose: String,
    actors: Vec<OrientationActor>,
    types: Vec<OrientationType>,
    core_flows: Vec<OrientationFlow>,
    walkthrough: OrientationWalkthrough,
    invariants: Vec<OrientationInvariant>,
    evidence: Vec<CodeEvidenceRef>,
}

fn validate_orientation_skeleton(
    skeleton: &OrientationSkeleton,
    context: &OrientationValidationContext,
) -> Result<(), OrientationValidationError>;
```

- 阶段 A 沿用当前完整源码或 bounded-source 精确切片；图谱和文件轮廓仍只是导航提示。
- 校验覆盖非空 purpose/actors/coreFlows/evidence/walkthrough、ID 唯一、所有 actor/evidence 引用闭合、证据路径/行号合法及 bounded-source 证据范围。
- 校验成功后整份 skeleton 不再修改；阶段 B 得到的是只读序列化投影,不能新增或改写 actor、flow、evidence。
- `orientationId/filePath/schemaVersion/coverage` 仍是最终合并时注入的后端事实,不进入模型输出。

### 2. 阶段 B 函数角色批次

```rust
struct OrientationRoleBatch {
    function_roles: Vec<FunctionRole>,
    supporting_capabilities: Vec<SupportingCapability>,
}

struct OrientationRoleBatchSpec {
    index: usize,
    fn_ids: Vec<String>,
    source_views: Vec<OrientationFunctionSourceView>,
}

enum OrientationFunctionSourceView {
    Exact { fn_id: String, numbered_source: String },
    SignatureOnly { fn_id: String, numbered_signature: String },
}

fn validate_orientation_role_batch(
    batch: &OrientationRoleBatch,
    spec: &OrientationRoleBatchSpec,
    frozen: &OrientationSkeleton,
) -> Result<(), OrientationValidationError>;
```

- 后端按已核验 roster 顺序稳定分批；首版每批最多 8 个函数,不得因源码长度或批次边界丢失函数。
- full-source 函数在本批获得带绝对行号的精确源码；bounded-source 已选函数获得精确源码,omitted 函数只获得现有轮廓中的签名并必须保守描述。
- `functionRoles` 必须恰好覆盖 `spec.fn_ids` 一次：漏函数、重复函数和批次外 `fnId` 都拒绝。
- actor/flow/evidence 引用只能来自 frozen skeleton；`supportingCapabilities.functionIds` 只能引用本批且 lane 为 supporting 的函数。
- core 角色仍必须引用至少一个合法 flow；supporting 角色仍必须使用空 `flowIds`；不为 omitted 函数伪造函数体 evidence。

### 3. 定向纠正

```text
generate batch
  -> parse + validate 成功:接受该批
  -> parse/contract validation 失败:
       correction(frozen skeleton,同一 batch spec,原始输出,确定性错误)
       -> parse + validate 成功:接受该批
       -> 再失败:整次定向失败
  -> provider/transport 失败:整次定向失败
```

- 每批最多一次纠正调用；纠正不能扩大 batch `fnId` 或 frozen ID 集合。
- 已成功批次在同一次定向尝试内不重跑；任一批最终失败时,所有内存中间产物随请求丢弃。
- 新的 WebSocket 重试是一次全新尝试,不复用上次阶段 A 或成功批次。

### 4. 确定性合并与原子提交

```rust
fn merge_orientation_card(
    skeleton: OrientationSkeleton,
    batches: Vec<(OrientationRoleBatchSpec, OrientationRoleBatch)>,
    backend: OrientationBackendFacts,
) -> Result<FileOrientationCard, OrientationValidationError>;

struct OrientationBackendFacts {
    schema_version: u32,
    orientation_id: String,
    file_path: String,
    coverage: OrientationCoverage,
    roster_fn_ids: Vec<String>,
}
```

```text
prepare source/graph/roster/cache identity
  -> cache hit:沿用 cache-hit -> card -> done
  -> cache miss:
       optional bounded-source plan
       -> stage A generate -> validate -> freeze
       -> stage B batch 1..N generate -> validate/correct
       -> merge in batch order;functionRoles 按全局 roster 顺序归位
       -> existing FileOrientationCard::validate
       -> reread source + refresh graph + reverify roster/identity
       -> put_orientation exactly once
       -> card -> done
```

- `supportingCapabilities` 按批次顺序追加,不跨批猜测同名能力是否应合并。
- 任一失败分支只发送可见 `error`,不得发送 `card/done`,不得创建或更新 `.fluid/orientations/<key>.json`。
- 最终卡线格式不变,所以 `ORIENTATION_SCHEMA_VERSION` 保持不变；生成语义改变,必须提升 `ORIENTATION_PROMPT_VERSION` 使旧卡自然 miss。
- `OrientationPhase` 与帧种类不变；现有 `orienting` status message 可分别报告“生成定向骨架”和“生成函数角色 i/N”。

## 切片依赖序

```text
S-ORI2-1 中间类型、独立校验与确定性合并
    -> S-ORI2-2 阶段 A/B Prompt、解析与稳定分批
        -> S-ORI2-3 全量/有界路由两阶段编排与整卡原子提交
            -> S-ORI2-4 单批定向纠正与整次失败语义
                -> S-ORI2-ACC 回归验收与文档收口
```

每刀开始前重新声明做/不做/判据,完成后立即追加 `docs/代码链路.md`；只有主数据流已经接入的刀才同步更新 `docs/技术方案.md`。功能刀不得夹带无关重构。

## S-ORI2-3 · 路由两阶段编排与整卡原子提交

- **状态**:已完成（2026-08-08）;full/bounded 生产 cache-miss 路径均已接线,纠正仍留给 `S-ORI2-4`。
- **做**:让 `run_orientation_emitting` 的 full-source 与 bounded-source cache-miss 路径共同调用阶段 A、逐批阶段 B、纯合并和最终 validator；保留调用后 source/graph/roster/identity 复验,只在末端调用一次 `put_orientation`。
- **不做**:本刀不增加纠正重试,不改帧种类、前端或缓存文件格式,不并发批次。
- **判据**:路由测试证明 full-source 调用数为 `1 + ceil(roster/8)`,bounded-source 为 `1 planner + 1 skeleton + ceil(roster/8)`；成功后重开零调用命中同一卡；阶段 A 或任一批失败、最终合并失败及调用中源码漂移均无缓存/无 card；抓取的供应商请求体不含 `response_format`。
- **触达**:`crates/fluid-server/src/routes.rs`,以及本刀需要调整的 orientation fixture/mock 断言。
- **落盘产物**:尚无纠正能力、但已满足整卡原子提交的生产两阶段主链路。

## S-ORI2-4 · 单批定向纠正与整次失败语义

- **做**:只对阶段 B 的解析/中间校验错误追加一次定向纠正；错误 Prompt 携带 frozen skeleton、同一批次边界、原始输出和确定性 validator message。
- **不做**:不纠正阶段 A,不重试 provider/transport 错误,不复跑同次请求里已成功批次,不保存失败中间态。
- **判据**:路由测试覆盖“首答非法、纠正合法”成功入整卡缓存；“首答与纠正都非法”只返回 error 且缓存目录不存在；随后新请求的调用序列从阶段 A 和第一批重新开始；纠正输出若引用批外 fnId/frozen 外 ID 仍被拒绝。
- **触达**:`crates/fluid-server/src/routes.rs`,`crates/fluid-server/src/context_assembler.rs`,相关 mock/fixture。
- **落盘产物**:符合“一批最多纠正一次,再失败则整次失败”的完整失败策略。

- **触达**:`docs/技术方案.md`,`docs/代码链路.md`,`SESSION_CHECKPOINT.md`,以及验收暴露的本功能测试文件。
- **落盘产物**:可提交的完整大切片和可复验的命令证据。

## 全程验证纪律

- AI 只生成 skeleton、批次角色和纠正候选；Rust parser/validator/merge、测试 runner 和缓存读写结果裁判合法性。
- 中间校验只做更早拒绝,最终 `FileOrientationCard::validate` 永远保留为合并后硬闸门。
- 原子性测试必须检查缓存文件系统状态,不能只根据未收到 `card` 推断“没有缓存”。
- 批次覆盖必须同时证明“不漏、不重、不越界”；只测试 happy path 不能证明 fnId 边界。
- bounded-source 必须同时证明已选函数体可见、omitted 函数体不可见、omitted 角色不伪造函数体 evidence。
- 整次重试测试必须用供应商请求序列证明阶段 A 与已成功批次确实重跑,不能依赖日志文本。
