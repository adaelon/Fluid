# 文件定向骨架同边界纠正切片方案

> 状态:实施中（2026-08-10）;`S-ORIC-1`、`S-ORIC-2` 已完成,`S-ORIC-ACC` 待实现。领域术语沿用 `CONTEXT.md`;本方案以 ADR-0027 修订 ADR-0025 中“阶段 A 不纠正”的失败策略,不改变 ADR-0025 的两阶段冻结/原子提交边界,也不改变 ADR-0026 的函数证据后端绑定。

## 目标与边界

**做**:

- 让 full-source 与 bounded-source 阶段 A Prompt 明确禁止在自然语言说明中使用“上游”“下游”及 `upstream`/`downstream` 字面词,必须直接点名已声明参与者。
- 阶段 A 首次输出发生 JSON 解析错误或 `validate_orientation_skeleton` 校验错误时,携原始无效输出与确定性错误发起一次同边界纠正。
- 纠正成功后仍经过同一 parser、同一 skeleton validator、后端 evidence 绑定及二次校验,随后才进入阶段 B。
- 第二次协议失败、纠正调用失败或后续任一既有硬闸失败时,保持整次定向失败且不写缓存。

**不做**:

- 不让小文件强制走 bounded-source planner,不改变 48k 阈值、取源预算、selected/omitted 分区或 SignatureOnly 语义。
- 不重试 provider/transport 失败,不递归纠正,不在一次请求内重新规划源码,不复跑已成功阶段。
- 不由后端替换自然语言、猜测 actor/flow/evidence 引用或放宽任何 validator。
- 不新增 WebSocket 帧、状态枚举、前端交互、半成品缓存或失败记录持久化。
- 不改变 `FileOrientationCard` 线格式、`ORIENTATION_SCHEMA_VERSION` 或现有合法卡集合。

## 已确认根因

- 小文件走 `build_orientation_skeleton_prompt`,大文件只多一轮 source planner 后走 `build_bounded_orientation_skeleton_prompt`;两条路径最终调用同一个 `validate_orientation_skeleton`。
- 两个 skeleton Prompt 当前只写“禁止无主语的上游/下游”,而 `contains_unbound_direction` 实际拒绝说明字段中出现任何“上游”“下游”或独立 `upstream`/`downstream` 词,提示与硬闸口径不完全一致。
- 当前阶段 A 首答只要 parse/validation 失败就立即结束;用户重试会创建全新请求,模型看不到上次输出与精确错误。
- bounded-source 解决的是上下文预算与证据范围,不是模型协议遵从;把所有文件切过去会增加成本并降低未选函数的信息量,不能针对本故障闭环。

## 冻结契约

### 1. Prompt 口径

full-source 与 bounded-source 的阶段 A system Prompt 使用相同规则:

```text
任何自然语言说明字段都不得出现“上游”“下游”、upstream 或 downstream；
方向必须直接点名 actors 中已声明的参与者 ID/名称，并由 step.fromActorId -> step.toActorId 给出结构方向。
```

- 该规则只是把 Prompt 对齐到现有 validator,不改变 validator 或已接受骨架的集合。
- 角色阶段、函数胶囊和追问仍消费后端已验证的参与者坐标,不新增另一套方向术语。

### 2. 单次纠正状态机

```text
optional bounded-source planner（最多一次）
  -> skeleton attempt 1
     -> provider/transport error: 整次失败,不纠正
     -> parse + validate 成功: evidence 绑定 -> 阶段 B
     -> parse/validate 失败:
          correction(
            original_system,
            original_user,
            original_invalid_output,
            deterministic_error
          )
          -> parse + validate 成功: evidence 绑定 -> 阶段 B
          -> provider/parse/validate 再失败: 整次失败
```

- `original_system` 与 `original_user` 必须逐字复用首次骨架请求,所以 full-source 仍是完整源码,bounded-source 仍是同一 planner selection 与 omitted 补集。
- 纠正 Prompt 只能追加“上次无效输出”“确定性校验错误”和重写完整 JSON 的指令;原输出明确标为非事实。
- 纠正不重跑 planner,不扩大可见源码、roster、actor/flow/evidence 集合,也不进入阶段 B 批次纠正计数。
- 只有首次 provider 已返回文本、且该文本未通过 parser/validator 时才允许纠正一次。
- `bind_exact_function_evidence` 或 enriched skeleton 二次校验失败属于后端绑定/不变量失败,不交给模型修补。

### 3. 失败与调用次数

| 场景 | 额外调用 | 结果 |
| --- | ---: | --- |
| 首次骨架合法 | 0 | 沿现有阶段 B/缓存链继续 |
| 首次骨架 parse/validation 失败,纠正合法 | 1 次 skeleton correction | 沿现有阶段 B/缓存链继续 |
| 首次骨架 provider/transport 失败 | 0 | 立即 error,无 card/done/缓存 |
| 纠正 provider/parse/validation 失败 | 不再追加 | 立即 error,无 card/done/缓存 |
| bounded-source 首次骨架协议失败 | 1 次 correction,planner 仍仅 1 次 | 使用完全相同的 selection 继续或失败 |
| 新的用户重试 | 新的一整次尝试 | 不复用上次无效输出或半成品 |

### 4. 缓存与版本

- 纠正前的 skeleton 和错误只驻留当前请求内存,不得写入 `.fluid/`。
- 最终卡仍只在阶段 A、全部阶段 B、整卡 validator 与调用后上下文复验全部成功后写一次。
- `ORIENTATION_SCHEMA_VERSION` 不变。
- `ORIENTATION_PROMPT_VERSION` 暂不提升:本次只让 Prompt 符合早已生效的 validator,既有缓存卡均已通过相同禁词硬闸;失败输出从未入缓存。若实现时扩大合法输出语义,必须回退本节重新决策。

## S-ORIC-1 · Prompt 对齐与纠正请求纯函数

- **状态**:已完成（2026-08-10）;full/bounded Prompt 已对齐现有方向词硬闸,同边界 skeleton correction 请求纯函数已落地但尚未接入生产路由。
- **做**:先增加 Prompt 契约红测;修改 full/bounded skeleton Prompt 的方向词规则;新增 `build_orientation_skeleton_correction_prompt(original_system, original_user, original_output, validation_error)` 纯函数。
- **不做**:不接生产路由,不发送真实 LLM 请求,不改 validator、版本常量或阶段 B Prompt。
- **判据**:测试证明 full/bounded 都禁止四个字面方向词;纠正请求逐字保留原 system/user 与 bounded selection,包含原无效输出和确定性错误,且明确不得扩大任何边界。
- **验证**:Prompt 红测先稳定断言失败,纠正构造器红测先因缺失符号编译失败;实现后 `cargo test -p fluid-server orientation` 67 passed/2 ignored,`cargo fmt --all -- --check` 与 `cargo clippy -p fluid-server -- -D warnings` 通过。
- **触达**:`crates/fluid-server/src/context_assembler.rs`,`docs/代码链路.md`。
- **落盘产物**:可由路由调用、但尚未改变生产行为的同边界纠正请求构造器。

## S-ORIC-2 · 路由单次纠正与失败原子性

- **状态**:已完成（2026-08-10）;full/bounded 生产路由共享阶段 A 单次协议纠正,provider/evidence/enriched 错误仍保持零纠正,失败不产出 card/done/缓存。
- **做**:先用 `flow.why` 含方向字面词复现小文件事故红测;在 `run_orientation_emitting` 中只捕获阶段 A 首答 parse/validator 错误并纠正一次;full/bounded 共用该分支。
- **不做**:不纠正 provider/transport、evidence 绑定或 enriched 二次校验错误;不重跑 planner;不改变帧协议、阶段 B 或缓存提交点。
- **判据**:
  - full-source 首答触发 `flow.why uses unbound upstream/downstream language; use actor IDs`,纠正合法后成功生成并命中缓存;
  - parse 错误同样只纠正一次;
  - 纠正再次非法或纠正调用失败时只有 error,无 card/done,且 `.fluid/orientations` 不存在;
  - bounded-source 请求序列严格为 `planner -> skeleton -> correction -> role batches`,planner 输入与 selection 不变;
  - 首答合法时调用次数与现状完全一致。
- **验证**:full-source 方向词事故红测先稳定得到 `status -> error`;实现后 23 个 orientation WebSocket 测试通过/2 ignored,定向专项 71 passed/2 ignored,`cargo fmt --all -- --check` 与 `cargo clippy -p fluid-server -- -D warnings` 通过。
- **触达**:`crates/fluid-server/src/routes.rs`,`crates/fluid-server/src/context_assembler.rs`,相关 route mock/fixture,`docs/代码链路.md`。
- **落盘产物**:小文件和大文件共享的一次阶段 A 协议纠正闭环。

## 全程验证纪律

- LLM 只生成首次/纠正候选;Rust parser、validator、测试 runner 与缓存文件系统状态裁判合法性。
- 回归测试必须先在现状代码上观察到稳定失败,再接实现转绿;不得通过删减错误样例或放宽断言“修复”测试。
- 调用次数必须从 mock 捕获的真实请求序列断言,不能依赖日志文本。
- 失败原子性必须检查无 `card`、无 `done` 且缓存目录未创建,三项缺一不可。
- bounded-source 必须断言 planner 只运行一次、纠正请求仍包含同一 selected 源码且不泄漏 omitted 函数体。
