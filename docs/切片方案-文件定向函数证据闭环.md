# 文件定向函数证据闭环切片方案

> 状态:实施中（2026-08-08）;`S-ORI3-1`、`S-ORI3-2`、`S-ORI3-3`、`S-ORI3-4` 已完成,`S-ORI3-ACC` 待实施。
> 领域术语沿用 `CONTEXT.md`;证据所有权决策见 `docs/adr/0026-文件定向函数证据后端绑定.md`。本方案修订 ADR-0025 的阶段 B 证据边界,但不改变两阶段骨架先行、整卡原子提交和最终 `FileOrientationCard::validate`。

## 目标与边界

**做**:

- 阶段 A 校验成功后,由后端为每个 `Exact` 函数建立一个可回切的函数跨度证据锚点,并冻结 `fnId -> evidenceId` 绑定。
- 阶段 B 只生成角色和外围能力的语义草稿,不再生成 `evidenceIds`。
- 后端把 `Exact` 角色绑定到自身函数锚点,把外围能力绑定到其全部成员函数锚点。
- `SignatureOnly` 角色继续保守存在且使用空证据,但不得进入 `supportingCapabilities`。
- 保留单批一次纠正;纠正只处理语义草稿的解析或边界违约,不再要求模型修补机械证据引用。
- 用本次“请求标识管理 + 空 evidenceIds”失败建立回归夹具,并补真实供应商 full/bounded smoke。

**不做**:

- 不放宽外围能力必须有源码证据的最终规则。
- 不让后端按名称或自然语言猜测哪条旧 evidence 支撑某个函数。
- 不从 `SignatureOnly` 的签名、图谱摘要或模型记忆伪造函数体证据。
- 不改变 `FileOrientationCard`、WebSocket 帧或前端类型,不持久化阶段 A/批次半成品。
- 不在本切片引入 LSP、跨函数静态数据流分析或新的供应商结构化输出能力。

## 失败证据与根因

- 真实错误 `orientation role batch 1 correction validation error: supporting capability 请求标识管理 must reference at least one evidence item` 只可能出现在纠正 JSON 已解析、但该能力的 `evidenceIds` 仍为空时。
- 当前阶段 A 只被要求为核心流、贯穿示例和不变量提供 evidence,并不保证每个外围函数都拥有锚点。
- 当前阶段 B 又只能引用阶段 A 的冻结 evidence,导致“模型必须引用证据”和“可引用集合未覆盖该函数”同时成立。
- 当前纠正只是把原输出和字符串错误再次交给模型;它不能创造合法锚点,只能删能力、重复空数组或误绑无关 evidence。
- ORI2 的 fixture 证明合法纠正响应可被编排接受,没有证明真实模型能从缺失的证据供给中恢复。

## 冻结契约

### 1. 阶段 B 只产语义草稿

```rust
struct FunctionRoleDraft {
    fn_id: String,
    lane: FunctionLane,
    flow_ids: Vec<String>,
    stage: String,
    receives_from_actor_ids: Vec<String>,
    consumes: Vec<String>,
    sends_to_actor_ids: Vec<String>,
    produces: Vec<String>,
    why: String,
}

struct SupportingCapabilityDraft {
    name: String,
    why: String,
    function_ids: Vec<String>,
}

struct OrientationRoleBatchDraft {
    function_roles: Vec<FunctionRoleDraft>,
    supporting_capabilities: Vec<SupportingCapabilityDraft>,
}
```

- 草稿 JSON 不含 `evidenceIds`;`deny_unknown_fields` 拒绝模型注入该字段、最终卡身份或批次身份。
- actor/flow/fnId 的冻结引用规则不变;每个批次 fnId 仍须恰好出现一次。
- Prompt 显式列出本批 `Exact` 与 `SignatureOnly` 集合;能力成员只能来自同一草稿中同时满足“来源为 Exact、lane 为 supporting”的函数。

### 2. 后端函数证据绑定

```rust
enum OrientationEvidenceSourceKind {
    Exact,
    SignatureOnly,
}

struct OrientationFunctionEvidenceSource {
    fn_id: String,
    kind: OrientationEvidenceSourceKind,
    line_range: [u32; 2],
    symbol: String,
}

struct OrientationFunctionEvidenceBindings {
    by_fn_id: BTreeMap<String, String>,
    evidence: Vec<CodeEvidenceRef>,
}

fn bind_exact_function_evidence(
    skeleton: OrientationSkeleton,
    sources: &[OrientationFunctionEvidenceSource],
    file_path: &str,
) -> Result<(OrientationSkeleton, OrientationFunctionEvidenceBindings),
            OrientationValidationError>;

fn materialize_orientation_role_batch(
    draft: OrientationRoleBatchDraft,
    spec: &OrientationRoleBatchSpec,
    frozen: &OrientationSkeleton,
    bindings: &OrientationFunctionEvidenceBindings,
) -> Result<OrientationRoleBatch, OrientationValidationError>;
```

绑定算法是确定性的:

1. 阶段 A 原始 skeleton 先按现有规则校验,拒绝悬空、越界或 bounded-source 外 evidence。
2. 按 skeleton evidence 原顺序重编号为连续 `E1..Em`,同步重写其 flow/walkthrough/invariant 引用。
3. 按后端 roster 顺序遍历 evidence source;`Exact` 若已有锚点恰好覆盖该函数完整跨度则复用,否则追加 `E{m+1}..`。
4. 锚点的路径、1-based 行范围与 symbol 只来自后端已核验 `FunctionSpan`;`SignatureOnly` 不创建绑定。
5. enriched skeleton 再过一次 `validate_orientation_skeleton`,成功后才作为阶段 B 的 frozen 坐标。

### 3. 草稿到最终字段的投影

| 输入条件 | 最终 `FunctionRole.evidenceIds` | 最终外围能力 |
|---|---|---|
| `Exact` role | 恰好包含自身后端函数锚点 | 可成为能力成员 |
| `SignatureOnly` role | `[]` | 不得成为能力成员 |
| 能力的成员全为本批 `Exact + supporting` | 按 `functionIds` 顺序绑定并去重全部成员锚点 | 接受 |
| 能力含 core、批外、未知或 `SignatureOnly` 函数 | 不投影 | 进入同批唯一纠正 |
| 模型输出任意 `evidenceIds` | 不解析为草稿 | 进入同批唯一纠正 |

- 后端绑定是从已核验函数跨度导出的机械事实,不是对能力名称或 `why` 的语义猜测。
- 能力至少有一个函数的既有规则保留;投影后其 evidence 必然非空且覆盖每个成员函数。
- 任意引用错误仍 fail closed;不得用“挑一个现有 E#”作为兜底。

### 4. 生产数据流与失败语义

```text
prepare source/graph/roster/cache identity
  -> stage A generate -> parse -> validate
  -> canonicalize stage-A IDs
  -> append/reuse Exact function-span anchors -> validate -> freeze
  -> for each role batch:
       generate semantic draft -> parse + validate
       -> materialize backend evidence bindings
       -> on parse/contract error: correct same draft once, then materialize
  -> merge in roster/batch order
  -> FileOrientationCard::validate
  -> reread source + refresh graph + reverify roster/identity
  -> put_orientation exactly once -> card -> done
```

- 绑定或物化失败与现有批次失败相同:只发 `error`,无 `card/done`,不创建或更新定向缓存。
- 已成功批次不因后续批次纠正而重跑;新的用户重试仍从阶段 A 开始。
- 最终卡 schema 不变,因此 `ORIENTATION_SCHEMA_VERSION` 不提升;阶段 B 协议和缓存语义改变,必须提升 `ORIENTATION_PROMPT_VERSION`。
- 旧缓存因 prompt version 自然 miss;旧模型输出若携 `evidenceIds`,只能通过一次纠正迁移为新草稿形状。

### 5. 事故回归样例

```json
{
  "functionRoles": [
    {
      "fnId": "allocate_request_id#127",
      "lane": "supporting",
      "flowIds": [],
      "stage": "分配请求标识",
      "receivesFromActorIds": ["scheduler"],
      "consumes": ["next_request_id"],
      "sendsToActorIds": ["scheduler"],
      "produces": ["RequestId"],
      "why": "为请求建立稳定标识"
    }
  ],
  "supportingCapabilities": [
    {
      "name": "请求标识管理",
      "why": "隔离并追踪并发请求",
      "functionIds": ["allocate_request_id#127"]
    }
  ]
}
```

若该函数为 `Exact` 且后端绑定为 `E7`,期望投影为角色 `evidenceIds:["E7"]`、能力 `evidenceIds:["E7"]`;模型没有填写或选择 evidence 的权力。若它是 `SignatureOnly`,角色证据为空且能力草稿必须被拒绝并纠正为不含该函数的能力集合。

## 全程验证纪律

- AI 只生成 skeleton 与阶段 B 语义草稿;函数跨度、evidence ID、角色/能力证据绑定和最终合法性由 Rust 决定。
- 先用失败测试复现 `请求标识管理` 空 evidence,再写实现转绿;不得先改 fixture 伪造成功。
- 每个最终能力必须逐成员证明至少一个 evidence 范围等于该成员已核验 Exact span。
- bounded-source 同时证明 selected Exact 有证据、omitted SignatureOnly 无证据且不进入能力,不能只检查最终非空。
- 真实供应商 smoke 是完成门禁而非 CI 常规测试;fixture 裁判协议,真实调用裁判 Prompt 可执行性。
- 任一失败分支都检查 `.fluid/orientations/` 的文件系统状态,不只根据“没收到 card”推断原子性。
